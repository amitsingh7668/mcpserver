You install a package. You trust the name. You've used it a hundred times. Then, quietly, your SSH keys, cloud tokens, Kubernetes secrets, and .env files travel to a server you've never heard of. This is the new normal in Python.

The Python ecosystem has spent the last 18 months under siege. What started as scattered typosquatting incidents has evolved into coordinated, multi-stage supply chain campaigns that compromise real packages — packages with millions of weekly downloads — and use them as delivery vehicles for infostealers, RATs, and persistent backdoors.

The damage is no longer theoretical. The attackers are well-funded, increasingly sophisticated, and they've found a reliable playbook that works across every major package registry. And the first line of defence — pip install — is, by design, almost entirely blind to it.

THE ATTACKS

Understanding the threat means walking through the incidents. These weren't theoretical CVEs. They were real packages, used by real engineers, in real production systems.

Ultralytics Critical

The popular ML vision library was backdoored via a compromised GitHub Actions cache. Attackers injected malicious code into the build phase and published poisoned versions (8.3.41, 8.3.42, 8.3.45, 8.3.46) using an unrevoked PyPI API token. The package has tens of millions of installs.

Cloud Credential Campaign Critical

ReversingLabs uncovered 20 malicious packages masquerading as cloud SDKs and time utilities (acloud-client, enumer-iam, snapshot-photo). Combined downloads exceeded 14,100 before detection, all harvesting AWS, Alibaba Cloud, and Tencent Cloud tokens via Base64-encoded payloads in setup.py.

Checkmarx Zero discovered a wave of packages mimicking the wildly popular colorama library. Cross-ecosystem name confusion was used — NPM package names repurposed to attack PyPI users. termncolor / colorinal High

A dependency chain attack: the innocent-looking termncolor package pulled in colorinal as a dependency, which executed DLL side-loading, established C2 communication, and enabled remote code execution. WHY PIP IS FLYING BLIND

pip is a fantastic installation tool. It is not a security tool. When you run pip install requests, pip fetches whatever the registry says is the latest version of requests. It does not verify that the version published today is the same code you audited last week. It does not lock transitive dependencies to known-good states. It does not alert you when a package you've been using for two years silently pushed a new version at 3am.

The LiteLLM attack exploited exactly this: a new version was published, millions of automated CI pipelines pulled it in on next build, and a .pth file was written that ran on every Python startup system-wide. No prompt. No warning. No lockfile check.

The Lockfile Gap

The absence of a requirements.lock in standard pip-based projects is the single biggest structural vulnerability in the Python ecosystem. A requirements.txt with requests>=2.28.0 is an open invitation. The attacker only needs to publish 2.28.1.

pip (Bare)

No lockfile by default

Resolves "latest compatible" at install time

No hash verification of downloaded wheels

Transitive deps can update silently

No separation of dev vs prod dependencies

pip install runs setup.py — arbitrary code execution

Poetry

poetry.lock pins every dep + transitive dep

SHA-256 hash verification on every install

Reproducible installs across all environments

Explicit dependency groups (dev, test, prod)

No silent upgrades — explicit poetry update required

Lockfile diffs are reviewable in PRs

THE POETRY SOLUTION

Poetry doesn't prevent malicious packages from existing on PyPI. What it does is give you a deterministic, auditable, hash-verified snapshot of your entire dependency tree — and it makes any change to that tree explicit and reviewable.

When you run poetry install, it reads the poetry.lock file and verifies the SHA-256 hash of every wheel before installing it. If the hash doesn't match what was recorded when the lockfile was last generated, the install fails. A compromised package version — pushed after you last ran poetry update — simply cannot sneak in.

# The old way — silent, unverified, dangerous
pip install litellm

# The Poetry way — pinned, hashed, auditable
poetry add litellm
# → Resolves + writes to poetry.lock with SHA-256 hashes
# → poetry.lock committed to git → changes visible in PRs
# → Every install: hash verified before extraction

# If TeamPCP pushes litellm 1.82.7 after your lockfile was written:
poetry install
✗ Hash mismatch for litellm 1.82.7 — installation aborted

The second layer of protection is visibility. Your poetry.lock lives in version control. When a dependency genuinely needs updating, the diff shows exactly which packages changed, which versions moved, and what hash was expected vs. what's new. A malicious update is no longer invisible — it's a green line in a PR.

Five Commands To Get Hardened

# 1. Initialize Poetry in an existing project
poetry init

# 2. Migrate your requirements.txt
cat requirements.txt | xargs poetry add

# 3. Commit the lockfile
git add poetry.lock pyproject.toml && git commit -m "chore: migrate to poetry"

# 4. Install in CI — always from lockfile, never resolve fresh
poetry install --no-root --only main

# 5. Audit for known CVEs (complements Poetry)
pip-audit --requirement <(poetry export -f requirements.txt)

THE BIGGER PICTURE

It would be a mistake to treat this as a "Python problem". The same month PyPI saw the num2words phishing breach, npm's chalk and debug maintainers were hit by an identical credential-phishing operation. Docker Hub containers were compromised in the same campaign window. The vector differs; the playbook is identical: find a trusted name, compromise a maintainer account, push a poisoned release, wait.

⚠ The Transitive Dependency Problem

The termncolor attack highlights a specific threat that lockfiles don't fully solve alone: a benign package pulling in a malicious dependency. With Poetry, at minimum, the transitive dependency is also pinned and hashed — so if colorinal's hash changes after your lockfile was generated, you're protected. Without a lockfile, the malicious dep silently resolves on every fresh install.

The 2025 RL Supply Chain Security Report found that while simple typosquatted packages on PyPI dropped by 85% year-over-year — thanks to improved PyPI moderation — the attacks that remained were dramatically more sophisticated. Attackers shifted from throwing bad packages at the wall to carefully compromising legitimate, trusted projects. Lower volume, higher impact.

What's unfolding isn't a string of unlucky breaks. It's the same pattern repeating across ecosystems: maintainers get phished, credentials get abused, and malicious code lingers far too long.

— Linux Security, 2025

WHAT TEAMS SHOULD DO NOW

Immediate Actions

Migrate to Poetry (or Pipenv) and commit your lockfile to version control today. Add poetry install --no-root to your CI pipeline. Add pip-audit or Dependabot to scan the lockfile on every PR. Treat any CI pipeline that runs a fresh pip install without a lockfile as a live vulnerability.

Structural Hardening

Enable PyPI Trusted Publishing for any packages you maintain — it creates cryptographic provenance attestations that allow PyPI, you, and your users to verify that a release was built from a specific git commit via a specific GitHub Actions workflow. If provenance attestations are absent on a release you didn't manually publish, something is wrong.

Runtime Detection

No lockfile prevents zero-day compromises to packages you already depend on. Complement dependency pinning with runtime monitoring: flag unexpected outbound connections initiated post-package-install, monitor for unusual IAM API call patterns (especially AssumeRole spikes), and treat any new .pth file appearing in your Python environment as an incident trigger.

The trust model that made PyPI and npm the most productive dependency ecosystems in the history of software is also their greatest liability. The answer isn't to abandon open source — it's to stop treating installation as a safe operation and start treating your dependency tree as an attack surface that deserves the same rigor as your own code.
